# SafeSiso content in Sanity

This folder is **not part of the website build**. It holds generated schema files
to be copied into a separate Sanity Studio project, and it is excluded from this
project's `tsconfig.json` because it imports the `sanity` package, which is
deliberately not a dependency here.

Nothing in this folder affects the site until `NEXT_PUBLIC_SANITY_PROJECT_ID` is
set. Until then the site reads its copy from `content/messages/`, which is also
the permanent fallback if the CMS is ever unreachable.

---

## What is editable, and what is not

| Editable in the CMS                                                   | Deliberately not                                  |
| --------------------------------------------------------------------- | ------------------------------------------------- |
| Home, How it works, About, Impact, SafeHer, Regions, FAQ, Media/Press | Privacy, Terms, Safety, navigation, forms, portal |

The reasoning is in [`../content/cms-namespaces.json`](../content/cms-namespaces.json).
The short version: the legal pages need PPAG/UNFPA sign-off, and the Safety page
tells a girl what the service can and cannot do and what happens if it thinks
she is in danger. An edit to either is a safety change, not a copy change, and
should go through review — not a CMS with no audit trail.

`lib/cms.ts` enforces this at read time as well. A `legal` document created in
the Studio is logged and ignored rather than applied.

## First-time setup

You need a free Sanity account. The free tier is well above what this site uses.

**1. Create the project** at [sanity.io/manage](https://www.sanity.io/manage).
Note the **project ID** — it looks like `abc12xyz`. Keep the dataset named
`production`.

**2. Create the Studio** somewhere outside this repository:

```bash
npm create sanity@latest -- --project <PROJECT_ID> --dataset production
```

**3. Install the schema.** From this repository:

```bash
npm run cms:schema        # regenerates sanity/schema/ from the English catalogue
```

Copy `sanity/schema/` into the Studio project, then reference it in
`sanity.config.ts`:

```ts
import { schemaTypes } from "./schema";

export default defineConfig({
  // ...
  schema: { types: schemaTypes },
});
```

**4. Seed it with the content that is already live.** This matters: it means
editors open the Studio and see the real site, rather than retyping 16 documents
by hand and introducing drift on day one.

```bash
npm run cms:seed          # writes review/cms-seed.ndjson
```

Then from the Studio project:

```bash
npx sanity dataset import /path/to/review/cms-seed.ndjson production
```

The document IDs are deterministic, so re-running the import updates the same
documents rather than creating duplicates.

**5. Allow the site to read the dataset.** Either make the dataset public
(Sanity manage → API → Datasets), or create a read token and set
`SANITY_API_READ_TOKEN`. Public is fine here — this is content that is published
on a public website anyway.

**6. Point the site at it.** In `.env.local`, and in Vercel:

```
NEXT_PUBLIC_SANITY_PROJECT_ID="abc12xyz"
NEXT_PUBLIC_SANITY_DATASET="production"
SANITY_API_READ_TOKEN=""          # only if the dataset is private
```

**7. Verify.** Run `npm run build` and check a page that the CMS manages. With
the seed imported and nothing edited yet, the site should look exactly as it did
before — that is the point of `npm run check:cms`, which asserts it.

## Day-to-day

- **An editor changed something and it has not appeared.** Content is cached for
  five minutes (`CMS_REVALIDATE_SECONDS` in `lib/cms.ts`). Wait, or redeploy.
- **A page went blank.** It should not be possible: empty CMS fields fall back to
  the local file per-key, and a failed fetch falls back to the whole local file.
  If it happens anyway, unset `NEXT_PUBLIC_SANITY_PROJECT_ID` to serve local
  content immediately, then investigate.
- **A key was added to a page in code.** Re-run `npm run cms:schema` and copy the
  schema over, or the Studio will not offer editors the new field.
- **Both languages are separate documents.** Editing English does not touch
  French. That is intentional: a French page silently reverting to English would
  be worse than it being briefly out of date.

## Files here

```
schema/
  index.ts               # the array to register in sanity.config.ts
  messages_<namespace>.ts  # one document type per editable namespace
```

Everything in `schema/` is generated by
[`../scripts/build-sanity-schema.mjs`](../scripts/build-sanity-schema.mjs) from
`content/messages/en/`. Do not edit it by hand — regenerate it, so the Studio and
the site cannot disagree about which keys exist.
